# SPEC - Respaldo programado del TPI (complemento nuevo, 10/11/2026)

## Objetivo y procedencia
Cerrar el objetivo 7 del integrador con una configuración diaria entregable y un ensayo REAL del Programador de tareas de Windows. U6 anterior sólo proponía horarios y no instaló tareas: no cambiar esa historia ni sus fuentes. Se reutiliza backup_foodstore.ps1 de U6 intacto, junto a tools/ps_common.ps1 y validaciones.sql, suministrados como contexto. OpenCode no ejecutará herramientas. El operador revisará todos los archivos y coordinará la ventana de laboratorio antes del único ensayo real.

## Archivos a generar completos
1. run_backup_job.ps1 (PowerShell7.5+): lee un JSON de configuración PRIVADO externo, valida requisitos, llama a U6 con un proceso pwsh hijo y deja resumen JSON sin secretos, en ruta privada nueva.
2. crear_tarea_diaria.ps1: construye e importa una única tarea diaria con primer disparo futuro elegible; permite ExportOnly. No borrar/reemplazar tarea preexistente. Nombre limitado a FoodStore-TPI-Lab-[GUIDhex32]. La tarea usa sólo el SID del usuario actual, InteractiveToken, LeastPrivilege. NO SYSTEM, NO Highest, NO credenciales/contraseñas almacenadas. Sin descargas, perfiles, bypass de política, servicios nuevos o cambios de permisos SQL.
3. tarea_diaria.template.xml: plantilla revisable con marcadores de SID/rutas; no contener datos personales del operador.
4. README.md: comando de ejemplo, requisitos, frecuencia diaria, responsables, controles/fallos y distinguir ensayo temporal de servicio productivo permanente.

## Contrato de configuración privada
ConfigPath es archivo JSON privado FUERA de Git: claves exactas U6Root, PgBin, DbUser, HostName, Port, PassFile, BackupWorkDir, WindowExpiresUtc. Usar -DateKind String. Resultado ResultPath es un archivo nuevo privado. No sobrescribirlo. HostName sólo127.0.0.1, Portválido, DbUseru5_bootstrap. U6Rootcontiene backup_foodstore.ps1, validaciones.sql y tools/ps_common.ps1. PgBincontiene clientes17. PassFileexisteypermanece externo; el JSON guarda una ruta, nunca su contenido. No imprimir contenido del JSON, nombres de usuarios del negocio ni diagnósticos completos.
El archivo ventana/config debe ser privado, sin herencia a otros usuarios. Validar ACL mediante SID del usuario actual, SYSTEM y Administradores, rechazando reparse points y cualquier ancestro .git; OWNER RIGHTS S-1-3-4 sólo se admite si su propietario resuelve al usuario actual. Aplicar esas reglas a ConfigPath, PassFile, BackupWorkDir y carpeta de ResultPath antes de leer o escribir secretos/dumps. No cambiar automáticamente ACL ajenas.
WindowExpiresUtc debe ser instanteUTC futuro y no más de60min desdeahora. El operador crea esta confirmación sólo en una ventana sin escritores. El runner antes de ejecutar verificará con psql que no hay otra sesión cliente en foodstore, y abortará ante otra sesión; es una precondición observada, NO un cerrojo contra nuevas conexiones. Declarar ese límite. Nunca afirmar automáticamente que se ha bloqueado el negocio. El runner exporta PGPASSFILE al proceso hijo, elimina otras variables libpq de redirección (PGHOSTADDR,PGSERVICE,PGSERVICEFILE,PGOPTIONS,PGPASSWORD), usa PGCONNECT_TIMEOUT. NO leer/imprimir la clave.
Invocar en proceso hijo pwsh -NoLogo -NoProfile -NonInteractive -File backup_foodstore.ps1 con HostName,Port,DbUser,PgBin,WorkDir y -ConfirmNoWrites sólo tras estas validaciones. El backupU6 tiene exit; no ejecutarlo dentro del mismo proceso. Comprobar código nativo inmediatamente. Suprimir diagnósticos nativos hacia salida entregable, guardarlos sólo privados si hacefalta. No poner claves en argv.
Tras éxito localizar exactamente un manifiesto SUCCESS nuevo con inicio después del comienzo del job, comprobar su archivo/tamaño/SHA256 y registrar resumen seguro: status,startedUtc,finishedUtc,sourceDatabase,backupFilebasename,backupBytes,backupSha256,baselinecounts/invalid/fingerprints,nativeExitCode. La carpeta privada de backups debe permanecer fuera del paquete. No presentar hash por sí solo como anonimato. Fallo devuelve1, sin SUCCESS fabricado. Resultado escrito con CreateNew. Una escritura de resultados fallida también debe provocar error.

## Tarea diaria
New-ScheduledTask/Register-ScheduledTask o XML oficial del scheduler Windows. StartBoundary explícito DateTimeOffset ISO8601, DailyCalendar DaysInterval1. En ensayo, primer disparo ~90s futuro para observar al programador iniciar realmente la tarea; luego deshabilitar/retirar únicamente esa tarea temporal tras obtener resultado y exportar evidencia. No usar Start-ScheduledTask para fingir disparo por horario. Registrar/exportar acción,principal(LogonType/RunLevel),trigger,LastRunTime,LastTaskResult y resumen. El XML entregado se sanea reemplazando SID/rutas locales por marcadores, con hash del original privado. La plantilla operativa propone02:00UTC-03, y requiere ventana confirmada cada ejecución; una confirmación expirada falla segura. Una configuración diaria registrada/ensayada/retirada NO equivale a servicio permanente activo.
Settings: MultipleInstancesPolicyIgnoreNew, no reintentos ciegos, límite10min, no despertar equipo, permitir ejecución en batería, no almacenar contraseña ni habilitar privilegios elevados. Directorios y dependencias deben existir. Escapar XML y argumentos sin concatenación ejecutable de texto arbitrario; aceptar rutas normales Windows con espacios, rechazar comillas dobles en rutas usadas en argv.

## Precisión de integración local de Codex posterior a Build
El contrato real del backup existente fue contrastado localmente, sin enviar sus fuentes a OpenCode: el manifiesto usa status, database, file (sólo basename), size, sha256, startUtc, endUtc y baseline. Se encuentra en BackupWorkDir/logs y el dump en BackupWorkDir/backups/file. baseline.counts y baseline.fingerprints tienen exactamente categoria, producto, usuario, pedido y detalle_pedido; fingerprints son MD5 de32caracteres hex minúsculos. baseline.invalid tiene productos y detalles, ambos cero. SHA256de64caracteres sólo verifica archivo dump. La primera SPEC no enumeraba estos campos y la propuesta Build declaró un contrato supuesto; se adapta el nuevo runner, sin modificar U6 ni fabricar manifiestos. ACL heredadas son aceptables si todas las entradas Allow se limitan a los SID permitidos; no se modifica la ACL del PGPASSFILE existente.
