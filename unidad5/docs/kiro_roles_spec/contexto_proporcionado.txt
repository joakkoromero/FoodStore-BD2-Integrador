rol_reportes. Logins obligatorios: app_web y admin_datos. Todos sin SUPERUSER,
CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS. Nunca ADMIN OPTION.
Agregar rol_propietario NOLOGIN que posee objetos y funciones protegidas;
NO otorgarle membresia a ningun login de aplicacion.

Agregar tambien rol_funciones NOLOGIN, sin membresia para ningun login.
Es dueno solamente de funciones SECURITY DEFINER. Concederle accesos internos
acotados: SELECT(id,email,contrasena,eliminado) y UPDATE(contrasena) en usuario;
SELECT(pedido_id,subtotal) en detalle; SELECT(id), UPDATE(total) en pedido;
MAINTAIN solo sobre la MV diaria. rol_propietario conserva las tablas.
No se abre la extension FNBC a la aplicacion; su guardia queda para su dueno.

Propuesta para discutir y justificar: app_web recibe lectura+escritura,
admin_datos recibe soporte. Membresias con INHERIT TRUE, SET FALSE,
ADMIN FALSE. Lectura catalogo/pedidos/detalle y columnas publicas usuario,
excluir siempre contrasena. Escritura solo columnas de negocio necesarias,
nunca subtotal/total derivados, nunca UPDATE credenciales ni DELETE usuario.
Especificar INSERT pedido(usuario_id,fecha,forma_pago) para que estado nazca
PENDIENTE; UPDATE pedido(estado,forma_pago,eliminado), INSERT detalle con sus
cuatro columnas de entrada, UPDATE detalle(cantidad,precio_unitario), DELETE
detalle para correcciones de pendientes. No DELETE pedido: usa baja logica.
Soporte puede leer columnas de contacto y cambiar telefono; solo admin_datos
ejecuta fn_resetear_password. Reportes accede solo agregados y usuario_anon.
fn_autenticar y fn_resetear_password se reconstruyen: SECURITY DEFINER,
propietario NOLOGIN, search_path pg_catalog, referencias calificadas,
REVOKE EXECUTE FROM PUBLIC. Auth valida bcrypt con pgcrypto, devuelve id o
NULL y registra resultado sin email/password/hash. Password reset solo admin.
No confundir cuentas usuario de negocio con roles LOGIN PostgreSQL.

Integracion minima de seguridad: mantenimiento interno de pedido.total y MV
diaria se ejecuta por funciones trigger SECURITY DEFINER acotadas, sin dar
UPDATE total ni MAINTAIN de MV a app_web. No cambiar reglas de negocio.
No otorgar blanket USAGE a secuencias identity: comprobar INSERT y negar
nextval/setval directos. Grants explicitos por tabla y por columna.
Revocar CREATE en esquema public y EXECUTE publico a funciones.
Default privileges bajo el rol creador correcto: negar acceso futuro por
defecto en public y permitir SELECT a rol_reportes solo en esquema separado
datos_anon, destinado exclusivamente a datos desidentificados.
